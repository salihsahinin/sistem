## AİLE A — MOTOR MEKANİZMASI + TERİM HARİTASI (Postgres kanonu)
A1. Postgres B-tree inişi: kök→iç→yaprak (Lehman-Yao B-link; `src/backend/access/nbtree/README`), sayfa 8 KB, fanout ↔ derinlik (kaç satırda kaç seviye — sayı+kaynak), yaprakta ne var (index tuple + TID = blok no + satır işaretçisi), `_bt_search`/`_bt_first`; heap fetch = TID ile heap sayfası + line pointer → tuple; NEDEN heap fetch zorunlu (indekste görünürlük yok — MVCC/xmin-xmax; HOT zinciri).
A2. Plan düğümleri + planlayıcı seçimi: Index Scan (seek + range, satır başına heap fetch) · Index Only Scan (visibility map all-visible ise heap atlanır; `INCLUDE` covering) · Bitmap Index Scan + Bitmap Heap Scan (çok satırda TID'leri sırala, heap'i sıralı oku) · Seq Scan; maliyet sabitleri (`seq_page_cost=1`, `random_page_cost=4`, `cpu_index_tuple_cost`, `effective_cache_size`), planlayıcının hangi seçicilikte hangi düğümü seçtiği (sayı varsa); `EXPLAIN (ANALYZE, BUFFERS)` ile heap fetch sayısı ("Heap Fetches: n", shared hit/read) — ölçüm yöntemi.
A3. Terim haritası (resmî dokümanla): SQL Server "Index Seek" ↔ "Index Scan" (+ Key Lookup/RID Lookup = heap fetch) · Postgres "Index Scan / Index Only Scan / Bitmap" (Postgres'te "seek" terimi var mı?) · MySQL/InnoDB clustered PK + secondary index → PK ile ikinci arama (EXPLAIN type ref/eq_ref/range/index) · SQLite `SEARCH … USING INDEX` ↔ `SCAN`. Salih'in cümlesi ("index seek, bazı kaynaklarda index scan; tek seferde atlama") hangi motor için ne kadar doğru — kaynaklı düzeltme.
A4. Heap ↔ clustered/kümelenmiş yerleşim: Postgres heap sırasızdır (`CLUSTER` tek-seferlik, korelasyon istatistiği `pg_stats.correlation`), InnoDB/SQL Server clustered index = tablo; "heap fetch" maliyeti korelasyona bağlı (sayı+kaynak); HOT (heap-only tuple) güncellemelerin indeks bakımı; `fillfactor`.
