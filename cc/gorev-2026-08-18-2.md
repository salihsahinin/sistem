## AİLE A — MEKANİZMA + ÖLÇÜLMÜŞ KAZANÇ (kolon ↔ satır; Redshift somutu; yazma semantiği)
A1. Kolon-deposu üstünlüğünün kaynağı (Abadi-Madden-Hachem 2008: satır deposunda dikey partisyon/indeks-only simülasyonu neden yetmez; geç materyalizasyon, sıkıştırma, blok iterasyonu, invisible join — hangi bileşen kaç kat; C-Store/Vertica, MonetDB/X100 vektörlü yürütme) — sayı + kaynak; kolon deposu ne zaman KAYBEDER (noktasal/geniş-satır getirme, küçük tablo, çok-kolon seçimi; tuple reconstruction maliyeti) — ölçüm.
A2. Redshift somut mekanikleri (resmî doküman): kolon başına 1 MB blok, zone map (blok min/max), sort key (compound/interleaved), dist key/style, sıkıştırma encoding'leri (AZ64/LZO/ZSTD/…; otomatik), `COPY` toplu yükleme, `VACUUM`/`ANALYZE`, küçük-yazım anti-deseni (tek satır INSERT), materialized view; her biri için sayı+URL; hangi kavramın gömülü/parquet karşılığı olduğu (yalnız kaynaklı eşleştirme).
A3. "Kolon-bazlı YAZMA" gerçekte ne: kolon depolarında yazım toplu/row-group'tur (immutable dosya, append + compaction; C-Store WS/RS + tuple mover; Redshift delta/sort region; DuckDB row group + WAL); tek-satır güncelleme = yeniden yazım; ölçülmüş yazım maliyeti/amplifikasyon; "kolon-bazlı okuma+yazma isteği" için doğru işlem birimi.
A4. Küçük ölçek: kolon↔satır farkının ÖLÇÜLDÜĞÜ en küçük veri seti/bellek-içi rejim (bellek-içi/önbellekte I/O tasarrufu → CPU/bant tasarrufuna döner mü; sayı); "I/O'ya hiç dokunmama" iddiasının sıcak-önbellek altında anlamı.

## AİLE B — GÖMÜLÜ HAZIR ÜRÜNLER JARVIS ÖLÇEĞİNDE (motor/format tarafı)
B1. DuckDB: native depolama ↔ parquet dış tablo ↔ sqlite_scanner (hangisi ne zaman; sürüm damgalı), COPY TO parquet seçenekleri (row_group_size, compression, PARTITION_BY, KV metadata), `parquet_metadata()`, EXPLAIN ANALYZE/profiling ile okunan byte, tek-yazıcı/eşzamanlılık modeli, **depolama biçimi sürümler arası kararlılığı** (native .duckdb dosyası ↔ parquet taşınabilirliği), Python/CLI kurulum boyutu, lisans; dbt-duckdb (model=parquet ihracı) — resmî.

## AİLE C — AMBAR OKUMA/YAZMA TASARIM DESENLERİ (gold = parquet "lakehouse-lite" + ölçüm + DEA-C01 eşleme)
C1. Dosya-tabanlı analitik katman deseni: medallion gold'un parquet olarak yazımı — partisyon (Hive-style; küçük veride "partisyonlama zararlı" eşiği), sort key seçimi, idempotent partisyon üstüne-yazma (functional DE) ↔ append-only + compaction; Iceberg/Delta/Hudi'nin gereksizlik eşiği (tek yazıcı, <1 GB, snapshot=git); DuckDB'nin delta/iceberg eklentileri (yalnız durum).
C2. Şema sözleşmesi + tazelik: parquet şema evrimi additive kuralı, dbt/great-expectations/dlt "schema contract" desenleri, üretim damgası (git SHA, kod SHA) parquet KV metadata'da; silver (SQLite) ↔ gold (parquet) eşdeğerlik testi (aynı sorgu iki motorda aynı sonuç) — yayımlanmış desen/araç.
C3. Ölçüm yöntemi: sorgu başına okunan byte / row group eleme (DuckDB profiling `EXPLAIN ANALYZE`, `pragma enable_profiling`, parquet_metadata) — küçük ölçek için "kolon katmanı kazandırdı mı" kanıt tasarımı; katman-oran metrikleri (bronz/silver/gold byte); benchmark disiplini (sıcak/soğuk önbellek, tekrar sayısı).
C4. Redshift ↔ gömülü eşleme (DEA-C01 öğrenme değeri, kaynaklı): sort key ↔ ORDER BY row-group · zone map ↔ parquet min/max · dist key ↔ (yok/partisyon) · encoding ↔ parquet dictionary/ZSTD · COPY ↔ COPY TO/FROM · VACUUM ↔ compaction/rewrite · ANALYZE ↔ metadata istatistikleri · materialized view ↔ gold parquet; ajan/LLM'in analitik sorgu yolu (DuckDB MCP durumu, text-to-SQL üzerinden gold sorgusu) — yalnız kaynaklı.
