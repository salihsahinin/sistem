## §1 — ALT-SORU 1: `loop-aday(l)` YÜKLEMİ (V46 formunda, SEÇENEKLİ)

### 1.1 Kanıt tabanı — koşulların kaynağı

| Koşul adayı | Ne ölçer | Kaynak | Damga |
|---|---|---|---|
| tekrar / hacim | kaç kez koştu | RPA uygunluk ölçütleri; endüstri eşiği **günde ~500 koşum** = "mükemmel aday" | [K] — danışmanlık kaynağı (nextpageit.com) |
| kural-tabanlılık | kararlar if-then'e dökülebiliyor mu | RPA + workflow↔agent ayrımı | [K] |
| **şekil-stabilitesi** | ardışık örneklerde aşama listesi değişmiyor mu | RPA'da AYRI ve ZORUNLU kriter; "tekrarlanabilir olmayan sürece otomasyon koymak durumu kötüleştirir" | [K] |
| düşük istisna oranı | akıştan sapan vaka payı | RPA kriter setleri | [K] |
| **deterministik done** | "bitti" makine-doğrulanabilir mi | RLVR: ödül deterministik kurallarla tanımlanır, ikili sinyal | [K] |
| ayrıştırılabilirlik | aşamalar arası bağımlılık zayıf mı | g20 K6 | [D-belge, g20 üzerinden arXiv:2604.02460] |

| bağlam-aşımı | girdi tek-ajan temiz belleğini aşıyor mu | g20 K1 | [D-belge] |

**Kritik negatifler (m.39 — uydurulmadı, arandı ve bulunamadı):**
- **`≥3` tekrar eşiğinin ampirik dayanağı YOK.** "Rule of Three" (Fowler, *Refactoring* 1999) sezgisel muhakemedir, deneyle doğrulanmamıştır [K]. **Bu, iç kaynağımızla BAĞIMSIZ YAKINSAMA:** `cc/rapor-2026-08-01-1.md` S9 aynı hükmü üç bağımsız kaynakla vermiş ve `[X→çürütülemedi]` damgalamış — *"m.43 eşiği bir GELENEK, kanıt değil"* [D-ölçüm, rapor-1:198,461]. İki bağımsız koşum aynı yere vardı.
- **Çok-aşamalı zincirler için birleşik bir "loop-aday" yüklemi literatürde YOK** — RPA/BPM ölçütleri tekil-süreç düzeyinde, workflow↔agent ölçütleri karar düzeyinde konuşuyor; ikisini çok-aşamalı zincire bağlayan tek formül bulunamadı [ARANMIŞ-NEGATİF, 2 bağımsız şerit].
- **Eşik-genişliğinin sayısallaştırıldığı çalışma bulunamadı** (kütüphane şişmesi / seçim maliyeti / $ bakım yükü) [ARANMIŞ-NEGATİF].

### 1.2 Üç seçenek (V46 formunda; m.37 karşıt-temel şartı gözetildi — ÖNERİ, kural değil)

**Seçenek L1 — DAR (m.43 simetrisi; minimum genişleme)**
```
loop-aday(l) ↔ tekrar(birim(l)) ≥ 3 ∧ mekanik(l) ∧ ¬yargı(l) ∧ ayrıştırılabilir(l)
```
*Zemin:* analoji/gelenek — mevcut kuralın bir koşulla genişletilmesi. *Aygıt:* yok (kural aktarımı).
**Bedel [ölçülü]:** şekil-stabilitesini ve done-yazılabilirliğini KAPSAMAZ ⇒ zorunlu vakada **YANLIŞ POZİTİF** üretir (§5.3: zincir bu yüklemden geçer, ama üç örneği üç farklı şekilde koşmuştur).

**Seçenek L2 — GENİŞ (endüstri ölçütlerinin tam aktarımı)**
```
loop-aday(l) ↔ tekrar(birim(l)) ≥ N
             ∧ stabil(şekil(l))                              # ardışık örneklerde aşama listesi sabit
             ∧ ∀i: ¬yargı(aşama_i)
             ∧ ∀i<n: şemalı(devir_i) ∧ denetlenebilir(devir_i)
             ∧ ∀i: deterministik(done_i)
             ∧ zayıf-bağımlı(aşamalar) ∧ girdi(l) > tek-ajan-temiz-bağlam
```
*Zemin:* beklenen-değer / tam-şartname (klasik otomasyon mühendisliği). *Aygıt:* RPA scoring matrix + RLVR doğrulanabilirlik.
**Bedel [ölçülü]:** bugünkü hiçbir zincir geçmez (§5.3 tablosu: 3 örneğin 3'ü de en az iki koşulda düşer) ⇒ **kural ölü doğar** — m.43'ün arıza sınıfının tekrarı (hakem Ç1).

**Seçenek L3 — KADEMELİ / ÖNEK-UZUNLUĞU (bu raporun işaretlediği aday) ✅**
```
# yüklem İKİLİ değil, en uzun geçerli ARDIŞIK ÖNEKİ döndürür
loop-aday(l) := max{ k ≤ n : ∀i ≤ k,
                       şemalı(devir_i) ∧ denetlenebilir(devir_i)
                     ∧ deterministik(done_i)
                     ∧ ¬yargı(aşama_i)
                     ∧ stabil(şekil(aşama_1..k)) }

loop-KUR(l)   ↔ loop-aday(l) ≥ 2 ∧ tekrar(aşama_1..loop-aday(l)) ≥ 3
kalan(l)      = aşama_{k+1..n}  →  skill-aday ∨ elle-kalır       # loop üyesi DEĞİL
terminal-istisnası: son halkanın ÇIKTISI anlatı olabilir; ARA devir olamaz
```
*Zemin (karşıt):* minimax-regret + MDL/Kolmogorov — "aynı işi yapan en kısa açıklama"; en kötü durum (tüm zinciri yanlış otomatikleştirmek) minimize edilir. L2'nin beklenen-değer zeminine **zıt**; canlılık şartı sağlanır (ikisi de bugün savunulan zeminler).
**Neden işaretlendi:** zorunlu vakada TEK doğru cevabı veren form budur (§5.3) — zinciri ne toptan kabul ne toptan reddediyor, **kesme noktasını buluyor**. Ve g20'nin `¬(K2∧K3) → pipeline KURULMAZ` kuralıyla aynı yapıda (yasak ara-devirdedir, terminal çıktıda değil).

### 3.2 VERİM TANIMI (#23 hiyerarşi telafisi — emir bu tanımı rapordan istedi)

Emir "verimli loop" ölçütünü kasten açık bıraktı. Önerilen tanım — **tek sayı değil, üç kapı**:

```
V1  devir-vergisi     = 1 − kalite(zincir) / kalite(monolit-referans)     # aynı bütçede

emekli(L)  ↔ V3 ≥ 1 − δ        # tek prompt yetişti ⇒ loop skill'e/tek çağrıya ÇÖKER
```

**Dürüstlük şerhi:** V1 bugün **HESAPLANAMAZ** — monolit referans koşumu hiç koşulmadı (g20 §7'nin (c) dilimi = masadaki K1-g; g21'de koşulmadı [D-ölçüm, kapsül]). ⇒ **Verim tanımı teslim edildi ama ölçülemez durumda; ölçülebilir hale gelmesi tek bir masa kararına bağlı.**

### 3.3 SKILL ↔ LOOP SINIRI

| | **skill** | **loop** |
|---|---|---|
| Yapı | tek-ajan kısayolu (tek çağrı içinde uygulanır) | çok-aşamalı zincir (aşamalar arası devir var) |
| Doğum kuralı | m.43: tekrar≥3 ∧ mekanik ∧ ¬yargı | §1.2 L3: önek-uzunluğu ≥2 ∧ tekrar≥3 |

**Sınır kuralı (öneri, lojik form):**
```
loop(L) → skill(S)  ↔  kalite(tek-çağrı) ≥ kalite(L) − ε  ∧  maliyet(tek-çağrı) < maliyet(L)
loop KALIR  ↔  ¬yukarıdaki  ∨  izlenebilirlik/hesap-verebilirlik zorunlu(L)
```
İkinci dal önemli: **denetlenebilirlik gerekçesiyle loop kalması meşrudur** — kalite eşitse bile. Bizim m.40b koşumumuz tam bu sınıftadır (tez↔antitez ayrımının değeri kalite değil **denetlenebilirliktir**).
