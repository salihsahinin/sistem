## KRİTİK BULGU (Claude Code Agent uyumu)

Promptfoo Python provider **HTTP API'ye bağımlı DEĞİL**: `call_api(prompt, options, context)` imzası herhangi bir Python fonksiyonunu sarar — dokümantasyon açıkça "subprocess çağrıları, lokal modeller, veya tamamen özel işlemler" örnekliyor [DESTEKLİ: promptfoo.dev/docs/providers/python/]. Bu, Jarvis'in ajan çağrı yüzeyinin (Claude Code Agent tool, HTTP API değil) promptfoo'ya `subprocess.run(["claude", ...])` sarmalayıcısıyla **teorik olarak oturabileceği** anlamına gelir — ama şu ÜÇ nokta doğrulanmadı: (a) Agent tool'un senkron/bloklayıcı semantiği ile promptfoo'nun paralel test-runner'ının (varsayılan concurrency) çakışması — Jarvis'te ajan-sayacı oturum-kümülatif (`pretool-ajan-fren.sh`), promptfoo bunu bilmez; (b) `tokenUsage`/`cost` alanlarını CC Agent'ın döndürmediği; (c) promptfoo'nun kendi retry/timeout mantığının paralel-kapı (PK-10) ayak-izi kısıtıyla çakışıp çakışmayacağı. **Sonuç: uyum imkânsız değil ama sarmalayıcı YAZILMADAN "DESTEKLİ" denemez — bu başlı başına bir M-2 borcu.**

## MODEL 1 — Hazır araç sarmalama (promptfoo)

**Temel:** deklaratif matris tanımı + var olan test-runner motoru; varsayım = eksen×hücre problemi zaten çözülmüş, tekerleği yeniden icat etmemek (m.6 "hazırı temel al").

**Ne demek:** `promptfooconfig.yaml`'da `prompts × providers × tests` matrisini tanımla, Python provider'ı `subprocess` ile Claude Code Agent çağrısına sar, `defaultTest`/assertion ile hücre-tipleme yap.

**Ne yaparım:** (1) `file://cc_agent_provider.py` yaz — `call_api` içinde CC Agent'ı subprocess/CLI ile çağır, dönen metni `output` alanına koy; (2) eksenleri `tests[].vars` olarak encode et; (3) `npx promptfoo eval -o results.json` ile koştur; (4) `results.json`'ı aile-1 §5 kütük şemasına (13 alan) dönüştüren küçük bir post-process script yaz (promptfoo kendi şeması İB-49/K-020 alanlarıyla birebir örtüşmüyor).

**Artı:** matris-tanım YAML'ı deklaratif, dış-eksen×iç-eksen'i elle nested-loop yazmadan ifade eder; CI/CD entegrasyonu hazır (JUnit XML dahil); topluluk bakımlı, promptfoo'nun kendi assertion kütüphanesi (regex, llm-rubric vb.) hazır gelir.

**Eksen:**
- **token:** kurulum ~orta-yüksek — provider script'i yazmak + CC Agent'a subprocess sarmalayıcı + post-process dönüştürücü ~3 ayrı script; hücre başına ek yük DÜŞÜK (promptfoo'nun kendi orkestrasyon overhead'i, LLM çağrısı hariç marjinal) — ama `T_hucre` ölçülmediği için (M-1 borcu) mutlak sayı verilemez, yalnız görece "az ek script" denebilir.
- **zaman:** kurulum ~1 gün (provider yazımı + test + post-process eşleme); İB-07/İB-49'un ELLE yaptığı işin bir kısmını (paralel koşum, JUnit rapor) devralır ama subprocess-CC Agent köprüsü test edilmemiş — ilk koşum "kurulum" değil "keşif" olur.
- **kalite (13 alandan kaçı otomatik):** `kosum_id`, `ts`, `sonuc` doğrudan gelir (3/13); `git_head`, `hucre_anahtari`, `hucre_tipi`, `eksen_degerleri`, `tekrar`, `model`, `toplama_yontemi`, `token_giris/cikis/onbellek`, `sure_ms`, `kosum_durumu` **elle eşlenmeli** (post-process script'te) — promptfoo'nun kendi `tokenUsage` alanı CC Agent'tan gelmiyorsa boş kalır. Yaklaşık **3-5/13 doğrudan, kalan 8-10 elle mühendislik**.
- **risk:** md.49 dışarı-veri — promptfoo lokal çalışır, `--share` bayrağı olmadıkça veri dışarı çıkmaz (DESTEKLİ değil, aile-1'de doğrulanmadı, `[?]`); bağımlılık = npm paketi + Node.js zinciri (Jarvis stdlib-only ilkesine aykırı, `tools/d2-eval.py` docstring'i "STDLIB ONLY" diyor — CLAUDE.md §6 "hazırı temel al" ile §2 "kaynak Türkçe/deterministik" arasında gerilim yok ama bakım-yükü npm güncellemeleriyle gelir); terk-riski = topluluk projesi, Jarvis'in kontrolü dışında API değişebilir; **Claude Code Agent uyumsuzluğu YUKARIDA "kritik bulgu"da işaretlendi — en büyük risk kalemi budur.**

**Hangi işlerde kullanılır:** CC Agent DIŞI, HTTP-erişilebilir model çağrılarını (örn. doğrudan Anthropic API ile Haiku/Sonnet karşılaştırması, prompt A/B) matrisleyen işler — burada provider zaten yerleşik (`anthropic:messages:...`), sarmalayıcı gerekmez.
**Kullanılmaz:** Jarvis'in bugünkü fiili işi olan Claude Code Agent çağrı matrisleri (İB-07 tarzı) — sarmalayıcı doğrulanmadan risk kabul edilemez.

## MODEL 2 — Minimal kendi harness (`d2-eval.py` deseninin genellemesi)

**Temel:** hücre-tipleme + deterministik toplama zaten m.6/Karar 65 ile kanonda var; İB-49 bunu 172 satırlık stdlib-only script'te KANITLADI — genelleme = icat değil, var olan deseni parametreleştirmek.

**`tools/d2-eval.py` okuması (somut):** 172 satır, `argparse` ile 5 mod (`--uretim`, `--sorular`, `--okuma`, `--sql`, `--kaydet`, `--ozet`); append-only jsonl kütük (`veri/d2-eval.jsonl`), her satırda `kaydet()` fonksiyonu `ts` + `git_head`'i OTOMATİK ekliyor (aile-1 §5'in 13 alanından 2'si zaten burada üretiliyor); `--ozet` modu gold CSV'ye (`veri/gorunum/v_d2_eval.csv`) deterministik agregasyon yapıyor (T1/T2 türü satır özeti, §3 ile birebir örtüşüyor). LLM'i script hiç ÇAĞIRMIYOR — işçi çıktısı dosya olarak veriliyor, harness yalnız ÖLÇÜYOR.

**Ne demek:** `d2-eval.py`'ı EKSEN-genel hale getir: `--eksen-sozlesme <json>` bayrağı ekle (aile-1 §1 EKSEN şeması), `kaydet()`'e §5'in 13 zorunlu alanını (özellikle `hucre_anahtari`, `hucre_tipi`, `token_*`) sabit alan olarak koy, `--ozet` modunu §3 T1-T5'e genişlet.

**Ne yaparım:** (1) mevcut `kaydet()`/`--ozet` iskeletini kopyala; (2) `EKSEN`/`HUCRE` şemasını (aile-1 §1-2) argparse+json ile oku; (3) hücre koşumunu (LLM çağrısı) script YAPMAZ — çağrı dışarıda (Agent tool/CC CLI) kalır, script yalnız SONUCU kaydeder (İB-49 ile aynı ayrım: harness ölçer, LLM üretir); (4) resume kuralını (`kalan_is = manifest − kütük`) tek fonksiyon olarak ekle.

**Artı:** stdlib-only (Jarvis ilkesiyle tam uyumlu), CC Agent'a HİÇBİR sarmalayıcı gerektirmez — çünkü script LLM'i çağırmıyor, dışarıdan (Agent tool çıktısı) besleniyor; kod zaten kanıtlı ve okunur (Türkçe docstring, m.2); aile-1 §5 şemasının 13 alanının TAMAMI script içinde birebir kodlanabilir (elle eşleme değil, doğrudan üretim).

**Eksen:**
- **token/zaman kurulum:** ~yarım gün — var olan 172 satırı ~250-300 satıra genişletmek (yeni bayraklar + eksen-okuma + T1-T5 agregasyon); hücre başına ek yük SIFIRA yakın (script yalnız bir jsonl satırı append ediyor, ağ çağrısı yok).
- **kalite (13/13):** hepsi doğrudan kodlanır çünkü şema zaten script'in EKSENİ — İB-49'un 2/13'ü (ts, git_head) kanıtlı, kalan 11'i aynı desenle eklenir. **13/13 potansiyel, en yüksek skor.**
- **risk:** md.49 dışarı-veri YOK (tamamen lokal, ağ çağrısı yalnız `d2` CLI derlemesi gibi yerel araçlarla, K-020 genellemesinde hiç yok); bağımlılık = sıfır (stdlib); terk-riski = Jarvis'in kendi kodu, terk edilmez (bakım Carvis'in işi); Claude Code Agent uyumsuzluğu YOK (script zaten Agent çağrısının SONUCUNU tüketiyor, çağrıyı sarmıyor).

**Hangi işlerde kullanılır:** CC Agent çağrı matrisleri dahil TÜM Jarvis-içi hücre-tipleme işleri (İB-07/İB-49/atlas aile×şerit); K-020'nin bugünkü ana ihtiyacı bu.
**Kullanılmaz:** dış API'lerle (OpenAI/Gemini karşılaştırma gibi) çok-sağlayıcılı matrisler — burada promptfoo'nun hazır provider kütüphanesi (M1) tekrar-yazımı önler; ayrıca CI/JUnit raporlama gibi promptfoo'nun hazır sunduğu yüzeyler burada elle yazılmalı (eksik).

## MODEL 3 — KARŞIT: hiç altyapı kurma (yalnız sözleşme + manifest/kütük)

**Temel:** M1 ve M2'nin İKİSİ de "önce harness inşa et" varsayıyor — bu varsayım YANLIŞ olabilir çünkü Jarvis'in bugünkü üç emsali (İB-07, İB-49, atlas aile×şerit) zaten AYRI script'ler olmadan, yalnız MANİFEST (json) + append-only kütük mekanizmasıyla koştu; matris sözleşmesi (aile-1 §1-2, JSON) + mevcut hareket-kütüğü (`tools/hareket-tablo.py`) + elle-çağrılan `kaydet()`-benzeri tek fonksiyon YETERLİ olabilir; harness inşası kendisi bir maliyet kalemidir ve M-1 (T_hücre ölçülmedi) ölçülmeden hangi otomasyonun karşılığını ödeyeceği bilinmiyor.

**Ne demek:** matris eksen/hücre sözleşmesini (aile-1 şeması) yalnız JSON dosyası olarak yaz, hiçbir yeni Python script YAZMA; her hücre koşumunda İŞÇİ AJAN kendi çıktısını doğrudan aile-1 §5 alan adlarıyla bir jsonl satırına ELLE (görev emrinde talimatla) yazsın, toplama İB-49'daki gibi AYRI bir tek-seferlik script (ad-hoc, kalıcı değil) ile yapılsın.

**Ne yaparım:** (1) sözleşme dosyasını (`veri/sozlesme/<is>-eksen.json`) yaz; (2) görev emrine (`gorev-emri-derleme` skill'i zaten bunu üretiyor) "çıktını şu 13 alanla jsonl satırı olarak `veri/<is>.jsonl`'a ekle" talimatını göm; (3) koşum bitince tek-seferlik `python3 -c "..."` ya da küçük ad-hoc script'le T1-T5 hesapla — kalıcı `tools/` dosyası açma.

**Artı:** SIFIR kurulum süresi/token'ı — bugün başlanabilir; hiçbir yeni bağımlılık/bakım yükü yok; M-1 ölçülene kadar "hangi otomasyon karşılığını öder" sorusuna cevap gerektirmez, kararı erteler (m.6 "tekrar-üretim varsayılmaz, kayıtla sağlanır" ilkesiyle en az varsayım).

**Eksen:**
- **token/zaman kurulum:** ~sıfır (sözleşme JSON'u zaten aile-1'de var); hücre başına ek yük İŞÇİ AJANIN kendi jsonl satırını yazma disiplinine bağlı — bu insan/ajan hatasına AÇIK (İB-07'nin tam olarak yaşadığı sorun: "resume tek sorguyla çıkmalı, İB-07'de ELLE yapıldı" aile-1 §5 RESUME KURALI notu).
- **zaman:** kurulum saatler değil DAKİKALAR; ama koşum-içi risk yüksek — her işçi ajan alan adlarını/tipini tutarlı yazmazsa kütük bozulur (Ö3 idempotency ihlali riski en yüksek modelde).
- **kalite:** 13 alanın TAMAMI teorik olarak yazılabilir ama HİÇBİRİ otomatik DEĞİL — hepsi işçi ajanın talimata uyma güvenilirliğine bağlı; `token_giris/cikis/sure_ms` gibi alanlar işçi ajanın kendi iç durumunu bilmesini gerektirir (CC Agent bunu döndürmeyebilir → M-1 borcu burada da AŞILMAZ, yalnız ertelenir).
- **risk:** md.49 dışarı-veri riski YOK; bağımlılık YOK; terk-riski YOK (hiç kod yok, terk edilecek şey yok); **ama en büyük risk BAŞKA yerde: veri kalitesi/tutarlılık riski** — deterministik toplama (Karar 65) girdi jsonl'un TİPLİ ve tutarlı olmasını şart koşuyor (aile-1 §2 Ö1), bu model o şartı otomasyonla değil disiplinle sağlıyor; İB-07 hakem tespiti ("eksen ile etiket-uzayı ayrımı" hatası) tam bu boşlukta oldu.

**Hangi işlerde kullanılır:** tek-seferlik/keşif matrisler (≤2-3 dış eksen değeri, düşük tekrar), M-1 ölçümünü ÜRETMEK için bizzat bu modelle bir pilot koşmak mantıklı (ölçüm borcunu kapatmak için önce en ucuz yoldan bir kez ölçmek gerekiyor — döngüsel değil, tam tersine ÖNCE bu, SONRA M1/M2 kararı).
**Kullanılmaz:** tekrarlı/kalıcı-üretim matrisler (İB-07 tarzı 60+ hücre) — disiplin riski büyür, hakem tespitindeki hata sınıfı tekrarlanır.

## ÖNERİLEN: **MODEL 2** (kendi harness'in genellemesi), gerekçe

Aile-1'in kendi kanıtı (`tools/d2-eval.py`) zaten Jarvis'in fiili işi olan CC Agent çağrı matrislerinde ÇALIŞIYOR ve stdlib-only ilkesiyle örtüşüyor; M1'in kritik bulgusu (Python provider HTTP'ye bağımlı değil, ama CC Agent köprüsü DOĞRULANMADI) onu şu an için riskli kılıyor; M3 ise M-1 ölçüm borcunu KAPATMAK için doğru İLK ADIM ama kalıcı çözüm değil — disiplin riski İB-07'de zaten bir hata sınıfı üretti. Öneri: **M3 ile bir pilot koş (M-1'i ölç), sonra M2'ye genişlet; M1'i yalnız dış-API (CC Agent dışı) matrisler için ayrı bir ihtiyaç olarak beklet.**

**Bu karar hangi ölçüm gelmeden VERİLEMEZ:** M-1 (`T_hücre` — tek-çağrı hücre maliyeti, aile-1 §4) ölçülmeden M1 vs M2'nin "token (hücre başına ek yük)" eksenindeki asıl farkı SAYISAL değil GÖRECELİ kalır; ayrıca M1'in CC Agent-subprocess köprüsünün gerçekten çalışıp çalışmadığı (yukarıdaki "kritik bulgu") bir deneme koşumu olmadan bilinemez — bu da ayrı bir doğrulama borcu (M-2 olarak adlandırılabilir, aile-1'in M-1'inden ayrı).
