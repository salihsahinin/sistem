## Hakem: kör noktalar
- Küçük-ölçek (10⁴-10⁵ satır) SQLite ölçümü YOK: bu ailede index SEARCH vs SCAN vs covering için ms/sayfa-okuma rakamı hiçbir tarafta yok; kanondaki 0,004-16,2 ms aralığı bu deneyle ilişkilendirilmemiş.
- 'İşaretçi→atlama' TOKEN KAZANCI ölçümü YOK: indeks/işaretçi ile tek satır getirmenin LLM bağlamına ham dosya dökmeye göre kaç token kazandırdığına dair hiçbir kaynak/ölçüm bulunmadı — aile A yalnız motor mekanizmasını kanıtladı, bağlam-bütçesi etkisi ölçülmedi.
- SQLite'ta tablo b-ağacına iniş sayacı YOK (hakem doğruladı): sqlite3_stmt_status 9 sayaç tanımlar (FULLSCAN_STEP, SORT, AUTOINDEX, VM_STEP, REPREPARE, RUN, FILTER_HIT, FILTER_MISS, MEMUSED); rowid-lookup/seek sayacı yok → Postgres 'Heap Fetches' / PG18 'index lookups' muadili SQLite'ta yalnız EQP metniyle nitel izlenir.
- Postgres satır-sayısı→B-tree seviye tablosu resmî dokümanda yok; seviye ölçümü pageinspect bt_metap().level ile yapılır, koşulmadı (Postgres kurulu değil).
- Planlayıcı 'hangi seçicilikte bitmap/seq scan' için resmî eşik yüzdesi yok; dolaşımdaki %5-10 kuralı birincil kaynakta doğrulanamadı.
- MySQL EXPLAIN type (eq_ref/ref/range/index) eşlemesi ve InnoDB covering ikincil indeksin ikinci inişi kaldırıp kaldırmadığı (MRR/ICP) birincil kaynaktan açılmadı.
- SQLite rowid takma adı (INTEGER PRIMARY KEY) ve WITHOUT ROWID tablolarda ikinci b-ağacı yolunun nasıl değiştiği bu koşumda birincil kaynaktan doğrulanmadı.
- Heap fetch mutlak maliyeti (µs, sürüm damgalı benchmark) hiçbir tarafta aranmadı.

## S1. Salih'in tanımı ↔ kanıt: ne doğru, ne düzeltilir
Salih (08-18): *"index'in kök-dal-yaprak katmanlarında gezinip aranan değerin heap'teki adresini bulması ve o adrese tek seferde 'atlaması' sürecine index seek (bazı kaynaklarda index scan) denir."*
- **Doğru çekirdek (A1-1 DARALDI, A3-1 SAĞLAM):** iniş kök sayfadan yaprağa (Lehman-Yao B-link; `_bt_search` döngüsü = inilen her seviye için 1 tur), yaprakta anahtar + **TID (blok no + satır işaretçisi)**, sonra TID ile heap sayfasına gidiş. Kaynak kodla doğrulandı (PG17 `nbtsearch.c:96-113`, `indexam.c:613-638`).
- **Düzeltme 1 — terim:** "index seek" **SQL Server** terimidir (Index Seek = SeekPredicates ile alt küme; heap fetch karşılığı **Key Lookup / RID Lookup**). **Postgres'te "seek" kelimesi geçmez** (14 birincil sayfa tarandı, 0 eşleşme); Postgres adı **Index Scan** (seek + aralık), ayrıca **Index Only Scan** ve **Bitmap Index Scan + Bitmap Heap Scan**. SQL Server'da "Index Scan" ise **tersini** (indeksin TÜM yapraklarını okuma) anlatır → "bazı kaynaklarda index scan denir" bir eş-anlam değil, motorlar arası **ad çakışmasıdır**. **SQLite** (Jarvis'in motoru): `EXPLAIN QUERY PLAN` **SEARCH … USING INDEX** ↔ **SCAN**; heap fetch karşılığı **ikinci ikili arama** (rowid ile tablo b-ağacına iniş; queryplanner: "two binary searches", maliyet ∝ (K+1)·logN). **InnoDB:** ikincil indeks fiziksel adres değil PK taşır → kümelenmiş indekste ikinci iniş (A3-3 SAĞLAM). Damgalar: SQL Server ver17 · PG17 · SQLite 3.51 · MySQL 8.4.
- **Düzeltme 2 — "tek seferde atlama":** düz Index Scan'de atlama **eşleşen her satır için ayrı** heap sayfası erişimidir (rastgele G/Ç); çok satırda planlayıcı **maliyete göre** (eşik yüzdesi değil; tenk1: 1 satır → Index Scan 0.29..8.30, 100 satır → Bitmap 5.06..224.98) TID'leri **fiziksel sıraya dizip** heap'i sıralı okuyan Bitmap çiftine geçer (A2-3). **Index Only Scan** heap'e hiç gitmeyebilir — ama yalnız görünürlük haritası (VM) sayfayı all-visible işaretlediyse; kalan ziyaretler `EXPLAIN ANALYZE` **"Heap Fetches: n"** sayacına yazılır (A2-2) → "heap'e gitmeme" garanti değil **ölçülen orandır**. PG13+ yaprak öğesi **posting list** (TID dizisi) taşıyabilir; **HOT zinciri** ile tek TID birden çok heap sürümü gezdirebilir (A1-3, A-YT6). Heap fetch'in **nedeni** = indekste **görünürlük (MVCC) yok**; SQLite'ta ikinci inişin nedeni farklıdır: indeks yaprağında satır değil rowid var (görünürlük katmanı yok) — analog, birebir değil (B1-1).
- **Düzeltilmiş tanım (Jarvis sözlüğü adayı, `mekanizma-terim`):** *İndeks araması = anahtarla indeks b-ağacında kökten yaprağa iniş (log N sayfa) → yapraktaki satır adresi (Postgres TID · SQLite rowid · SQL Server RID/kümelenmiş anahtar · InnoDB PK) → adresle satırın kendisine ikinci erişim (heap fetch / ikinci b-ağacı inişi / Key Lookup); kapsayan (covering) indeks ikinci erişimi kaldırır. Adı motora göre değişir; mekanizma aynıdır.*

## S3. Jarvis sondajı (deterministik, bu oturum) — motor zaten "seek" yapıyor; kazanç motorda değil, ERİŞİM DİSİPLİNİNDE
- Noktasal sorgular zaten indeksli: PK `kayit_id=?` **0,004 ms**; `dosya_id`+satır aralığı 0,005-0,040 ms (bileşik `(dosya_id,satir_bas,satir_son)` indeksi 3,6× daha hızlı — 0,011 ms; hepsi µs mertebesi); `referans(ref_turu,ref_deger)`→`kayit` JOIN 143 satır 0,10 ms; `karar_borcu(borc_id=?)` 0,007 ms. İndekssiz: `metin LIKE` **SCAN 16,2 ms**, `satir_bas=?` SCAN 5,3 ms (`.expert` doğru indeksi önerdi). Sonuç: **10⁴-10⁵ satırda motor ayarları µs kazandırır** (hakem kör noktası: bu ölçekte literatür ölçümü yok — bu sondaj ilk yerel ölçümdür, m.29 deneysel).
- **Asıl kazanç token'da:** tam-dosya okuma ↔ tek-blok getirme oranı **kapsül 27× · pano 27× · tüzük 54× · KILAVUZ 78× · rapor-15-6 471× · senaryo-defteri 563×** (blok medyanı 40 token; dosya ort. 5,7k token; `karar-borcu.jsonl` 67 kalem → tek kalem 67×). ## S4. TASARIM — Jarvis'te "indeks araması" erişim yolu, hazırı temel alarak (Salih: "0'dan inşa etme")
**İlke:** Postgres mantığı Jarvis'e **kod olarak değil, ERİŞİM DİSİPLİNİ + mevcut motorun doğru kullanımı** olarak girer. Motor (SQLite) inişi zaten yapıyor; eksik olan (i) Carvis'in satır-bazlı işte bu yolu KULLANMASI (bütün dosya yerine adres→aralık), (ii) indeks↔heap tazelik kontrolü, (iii) motor hijyeni (istatistik, covering, test), (iv) kodsuz satır yüzeyi.

**Katmanlar (kök→dal→yaprak→heap):**
1. **Kök (bağlamda):** kapsül/pano/CLAUDE.md işaretçileri (m.20) — zaten yüklü.
2. **Dal (anahtarlı indeks):** silver `anahtar(anahtar_id)` · `referans(ref_turu,ref_deger)` · `karar_borcu(borc_id)` · `dosya(dosya_id)` — hepsi SEARCH (ölçüldü). Sorgu = anahtar (kart/KB/madde/terim/skill) → `kayit_id` listesi.
3. **Yaprak (adres):** `kayit_id` = yol#satır-aralığı#sha8.
4. **Heap fetch (iki yol, tercih sırası):** (a) silver `kayit.metin` (covering — dosyaya inmeden; 0,004 ms) **sha8 = uretim damgası ile birlikte** · (b) dosyadan `sed -n a,bp` / Read(offset,limit) — sha8 yeniden hesaplanır; **tutmuyorsa BAYAT** → dosyada `grep -n` ile yeniden konumla + `tools/katman-hatti.py` (silver ~5 sn) koş.
5. **Yazım (OLTP-sınıfı):** satır **bronz'a** yazılır (jsonl/md, append ya da yerinde düzeltme), silver **yeniden üretilir** (functional DE, idempotens kanıtlı) — UPSERT yalnız yükleyici içinde (INSERT OR REPLACE) kalır; HOT ilkesi ("indeksli alanı değiştirme") artımlı yazım gelirse geçerli.

## S6. Sınırlar / yeniden-açma koşulları
- Küçük-ölçek (10⁴-10⁵ satır) SQLite seek↔scan ölçümü literatürde YOK (üç hakem de); bu raporun µs/ms rakamları tek makine, tek koşum, m.29 deneysel — ≥10 koşumla kalibre.
- "İşaretçi→atlama" token kazancı için dış metodolojili ölçüm YOK (Anthropic tek illüstratif rakam 150k→2k, K); yerel oran (27-563×) tam-dosya token kestirimi (bytes/4) üzerinden — gerçek Read çağrısı ölçümü İB-29 ile.
- Aile C tezi V26'da 1 TUTMUYOR (C2-2 SCIP "LSIF'in yerine geçer" yanlış) → C tezinin tüm bulguları K; hakem yapı-taşları kendi doğrulamasıyla D. 2 ERİŞİLEMEDİ (C1-3 SDK sayfası; bir Postgres doküman 404).
- Postgres kurulu değil → pageinspect seviye ölçümü, `Heap Fetches` gözlemi koşulmadı; kavram sözlüğü olarak girer. DuckDB eklenti sürüm damgası K.
