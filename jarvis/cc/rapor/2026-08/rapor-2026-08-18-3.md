| **Index Scan** | indeks inişi + satır başına heap erişimi | `SEARCH … USING INDEX (kolon=?)` | — | PK 0,004 ms |
| **Index Only Scan** | yalnız indeksten cevap (PG: görünürlük haritasına bağlı) | `SCAN/SEARCH … USING COVERING INDEX` (SQLite'ta VM koşulu YOK — daima kazanır) | parquet kolon-chunk = "yalnız gereken kolon" | `count(*)` SCAN COVERING 0,07 ms; Q1 covering 1,3 ms |
| **Bitmap Index + Heap Scan** | çok satırda TID'leri sırala, heap'i sıralı oku | doğrudan karşılığı yok; en yakın `MULTI-INDEX OR` (birden çok indeksi birleştirir) | row-group atlama (zone map min/max, bloom) | OR sorgusu 0,01 ms |
| **TID (Range) Scan** | fiziksel adresle/aralıkla erişim | `SEARCH … USING INTEGER PRIMARY KEY (rowid>? AND rowid<?)` | row-group id | rowid BETWEEN 0,03 ms |
| **Skip Scan** (PG18) | öncü kolon kısıtsızken bileşik indeksin sonraki kolonu | `SEARCH … (ANY(ref_turu) AND ref_deger=?)` — **yalnız ANALYZE sonrası** (stat1; ~18 tekrar/değer eşiği) | — | 1,08 → 0,02 ms (54×) |
| **Parallel Scan** | işçi süreçler (PG: tablo ≥8 MB, log-3 merdiven) | YOK (tek iş parçacığı) | row-group başına paralel (kayit 11 row group) | girmez (SQLite) |
| **Sample Scan** (TABLESAMPLE) | blok/satır örnekleme | YOK (`ORDER BY random()` = tam tarama) | `USING SAMPLE` reservoir/bernoulli/system (REPEATABLE) | keşif için |
| — (SQLite'a özgü) | sorgu-anı geçici indeks | `SEARCH … USING AUTOMATIC COVERING INDEX` = **kalıcı indeks adayı sinyali** | — | join indekssiz kolon 28,3 ms |
| — | sıralama | `USE TEMP B-TREE FOR ORDER BY` = indeks-sıralı erişim fırsatı | — | Q1 planında var |
Plan okuma (A-YT1): PG `Index Cond` = indeksle karşılanan · `Filter` = satır getirildikten sonra · `Recheck/Heap Blocks/Heap Fetches` yalnız EXPLAIN ANALYZE; SQLite'ta EQP metni + `sqlite3_stmt_status` sayaçları (FULLSCAN_STEP ≈ N → tam tarama · AUTOINDEX>0 → indeks fırsatı · SORT>0 → sıralı-erişim fırsatı; C-YT4/5) — Python stdlib'ten sayaçlara erişim yok (ctypes ile mümkün, taşınabilirlik ölçülmedi).

## S2. Seçim kuralı — "hangi soruda hangi tarama" (kanıtlı çekirdek; sayısal eşik YOK, ölçüm var)
1. **Karar değişkeni yüzde değil DOKUNULACAK SAYFA sayısıdır** (A-YT2 D): "%5-10 seçicilikte seq scan" kuralı birincil kaynakta YOK (A-04 X); tek kategorik ifade "tek sayfaya sığan tablo → daima seq scan". Jarvis: page_count/dbstat ile ölçmeden yüzde kuralı yazılmaz.
2. **"Küçük veri → her şeyi seq scan" varsayılmaz** (C-YT7): SQLite ANALYZE'siz motor küçük veride bile AUTOMATIC INDEX kurar; her sorgu tipi EQP ile ölçülür.
3. **Önce ANALYZE / PRAGMA optimize** (B-YT2, C-YT6): stat1 yokken skip-scan KOŞULSUZ kapalı, planlayıcı N=1.000.000/10 tekrar varsayar; Jarvis'te ANALYZE hiç koşmamış (54× ölçüldü). Kural: silver yenilemesi sonrası ANALYZE (ya da bağlantı kapanışında `PRAGMA optimize`); plan testinin ön-koşulu "stat1 var".
4. **Noktasal/anahtarlı soru → SEARCH (indeks)**; **tam agregasyon → SCAN kabul** (küçük tablo; covering varsa daha iyi); **çok-kolonlu agregasyon → parquet/DuckDB** (kolon katmanı, KB-55); **metin araması bronz'da → rg** (B-YT8; FTS5 eşiği kaynaksız); **örnekleme/keşif → DuckDB USING SAMPLE** (SQLite'ta yok).
5. **AUTOMATIC INDEX görüldü → kalıcı indeks adayı** (B-YT3); **LIKE önek → SEARCH bekleme** (6 koşul; aralık yüklemi `>= 'core/' AND < 'core0'` ya da NOCASE indeks — B-YT4); **plan sabitliği garanti değil** (QPSG kapalı; çare merdiveni ANALYZE → CROSS JOIN → unlikely() → unary + → INDEXED BY son çare — B-YT5).
6. **DuckDB ← sqlite_scanner filter pushdown YOK** (B-YT6): SQLite üstünden DuckDB filtreli sorgu SQLite indeksinden yararlanmaz → OLTP SQLite'ta, OLAP parquet'te (KB-55 deseniyle tutarlı).
7. **Ajan erişim yolu** (C-YT1 D, kural-sayı yok): hafif tanımlayıcı tut, hedefli sorgu, head/tail örnekle; motorlar-arası seçim ölçümü hiçbir kaynakta yok (üç hakem) → Jarvis'in kendi sayacı (İB-29) tek kanıt yolu.
